## CONVENTIONS

**WHAT BELONGS HERE.** The test is ownership, not subject matter: if the artifact is shared by every model column, or is the tooling that guards one, it is platform work and it files here. If it is evidence about one model's physics, it files on that model's roadmap even when it touches a shared file.

| Platform (this roadmap) | Model roadmap |
| --- | --- |
| [`MODELS.md`](../MODELS.md) structure: the criteria set, the score-board, the cell rules | a single model's icons and evidence cells |
| [`ONBOARDING_MODELS.md`](../ONBOARDING_MODELS.md), [`REPRODUCE.md`](../REPRODUCE.md), [`AI_HYGIENE.md`](../AI_HYGIENE.md), [`dev_docs/`](.) standards | a model's own findings, notes, question tracker |
| [`dev_docs/utils/`](utils) checkers and procedural tooling | a model's research scripts under its `research/scripts/` |
| Cross-model conventions (status vocabulary, regime column, claim labels) | a model's task ladder and gates |

**WHAT GOES IN A GITHUB ISSUE (2026-08-01, [T5](tasks/t5_task_details.md)).** Tasks are tracked in the roadmaps of this repository, never in issues. A **GitHub issue is for a platform issue**: something reproducible and closable that is wrong with the platform itself, such as an engine bug, a checker that misfires, an install or reproduction failure, or a document that states something untrue. Research work is a roadmap row with a task document behind it, however small the piece. Proposals, questions and offers of contribution belong in [Discussions](https://github.com/openwave-labs/openwave/discussions); one becomes a row when someone scopes it into work. The reason is that a roadmap edit is a tracked diff, which is what a file several authors touch needs, while an issue body edits in place with a history its own author can delete.

**HOW REVIEW WORKS (2026-08-01, [T7](tasks/t7_task_details.md)).** One document, one merge: review comments are settled in the PR thread before merging, small or mechanical fixes are applied to the branch at merge and announced there, addenda to a frozen document are batched to a review point, and a follow-up PR is for new work only. The reviewer's procedure, including the maintainer's own coordination PRs, is [`PR_REVIEW_STANDARDS.md § 10.3`](PR_REVIEW_STANDARDS.md#103-one-document-one-merge); the contributor-facing statement is [`CONTRIBUTING.md § How review works`](../CONTRIBUTING.md#how-review-works).

**T-ID SCHEME.** Platform tasks are numbered `T<n>`, assigned in order of creation and never reused. They are deliberately outside the `M<model>.<n>` space so a platform task cannot be mistaken for one model's work. A task migrated in from a model roadmap keeps a `(was M5.29)` note in its row and its change-log entry; the old ID is not reused.

**TASK DOCS.** One doc per task at [`tasks/t<n>_task_details.md`](tasks), same anatomy as the model roadmaps use (PLANNING → DEVIATIONS LOG → FINDINGS, blindspots table, `Gated by` line, cross-links table). Conversation records for a task, when the input came from a group thread or an author exchange, sit beside it as `t<n>_convo.md`.

**DONE ORDER.** Newly closed tasks are APPENDED at the END of the DONE list, so it reads in order of completion.

**T3 RAN THE SAME DAY IT WAS FILED, AND CHANGED ITS OWN ANSWER (2026-07-28).** The cell budget was raised 55 → 65, but not for the reason the task was filed on. "One number across two files" is arithmetically wrong: [`check_models_md.py`](utils/check_models_md.py) counts prose only, while [`check_roadmaps.py`](utils/check_roadmaps.py) counts link labels and has no status tag to strip, so the same number permits about a third more here. Measuring reading load alone, the first pass concluded the two caps already rendered the same cell and recommended keeping 55. The user's actual reason for the raise was column geometry, which that pass never measured: the 2026-07-25 split gave each model's summary column 0.910 of its table's width against a roadmap `Description`'s 0.668, a 1.36× ratio putting the equivalent cap in the bracket **[49, 74]** with 65 inside. Both ends are re-runnable ([`models_cell_stats.py`](utils/models_cell_stats.py)), so the next structural change tests the number instead of inheriting it. Folded in on the user's call: five stale "matrix cell links a script" sites repointed, the linter's missing sixth check documented, criteria counts 21 → 31 in three model docs (a [T1](tasks/t1_task_details.md) tail), and the [`MODELS.md`](../MODELS.md) rule prose halved.

**T4 FILED: THE CLEAN ROOM IS PROCEDURE, NOT PHYSICS (2026-07-30).** Answering "how do we actually build the M8.5-A context firewall" produced decisions that turned out to be about none of M8's subject matter: where the room lives, which tools are withheld, what may enter the packet, who audits it, and what order the commits go in. The [ownership test](#conventions) files those here and leaves the reproduction itself on the [M8 roadmap](../openwave/xperiments/m8_mit/research/m8_roadmap.md). The exercise already produced one finding worth a standard: an obvious sibling-of-the-repository folder failed, because a `CLAUDE.md` on its ancestor path instructs an agent to read the quarantined tree on the first turn, before the packet is opened, and nothing inside the room would have shown it. Two decisions worth recording ahead of the run: the packet carries two generators rather than all 120 elements, so the closure gate can fail rather than being true by construction, and each packet part gets a mechanical audit (`diff`, a closure count) rather than a judgment call, since the same maintainer assembles and audits it. The standard is written in block E, after adjudication, so it records what held rather than what was planned: [T4](tasks/t4_task_details.md).

**T5 FILED: EVALUATE ISSUE-BASED TRACKING, WITH THE QA LINE DRAWN FIRST (2026-07-31).** In the 24 hours around the M8.5-A freeze, the coordination edits alone took three reviewed merges (#382, #383, #384); for a fork-based author each such edit is a full fork → PR → DCO cycle, and the cost is linear in edits × authors. T5 EVALUATES moving live coordination state to GitHub Issues + Projects v2 while the citable record stays in git, under one boundary rule: an issue holds only what nothing needs to cite; declining to migrate is a first-class outcome. One decision was fixed before any consultation: authors receive no triage or project write, since completion validation and board state are the maintainers' quality-assurance role. Two named costs follow, recorded rather than negotiated: the author's column becomes intent-driven but maintainer-operated, and every state change costs a maintainer action, so the migration relocates that friction to the maintainers rather than deleting it. The trade-off table and the evidential-vs-scheduling gate split are in the task doc. Nothing migrates before the model authors are consulted, and the M8 column not before M8.5-A closes, since its frozen protocol pins the task-spec path it pairs with: [T5](tasks/t5_task_details.md).

**T2 PROPOSED AND DEFERRED THE SAME DAY (2026-07-28, user proposal + user decision, as M5.30).** A per-column 0-10 score was proposed for the score-board (icon weights 1 / 0.5 / -1 / 0 over the full criteria set, rescaled onto 0-10), analysed in full, and parked with a re-open trigger. It reproduces exactly and has two defects: untested rows pull a column to the 5.0 midpoint, so silence reads as "average model" rather than "unknown" (M8 scores 5.1 on ONE attempted criterion out of 22), and ❌ = -1 sits below 🚧 = 0, so publishing a failure costs more than never running the test. The repair (coverage `A/N` beside score-on-attempted `10 × (✅ + 0.5⚠️)/A`) fixes both and adds a third defect, the user's catch: at small samples it is unstable, since M8 would print 10.0 on one validated row. **Deferred** because the score-board already separates covered from not-covered and orders the columns, so a scalar is not worth the author friction at today's coverage. Revisit on a critical mass of tested rows, with a minimum-coverage gate or shrinkage as the candidate cures. Full analysis, sensitivity band and the no-reordering pre-commitment: [T2](tasks/t2_task_details.md).

**T4 CLOSED: THE CLEAN ROOM IS A STANDARD, WRITTEN FROM THE RUN (2026-08-01).** [`CLEAN_ROOM_STANDARDS.md`](CLEAN_ROOM_STANDARDS.md) exists, written after the M8.5-A arc completed (packet [#389](https://github.com/openwave-labs/openwave/pull/389), commitment [#391](https://github.com/openwave-labs/openwave/pull/391), adjudication REPRODUCED [#392](https://github.com/openwave-labs/openwave/pull/392), audit [#394](https://github.com/openwave-labs/openwave/pull/394)), so it records what held rather than what was planned; the planning doc's misses are in its own deviations log and folded into the standard as § 13, the nine failure modes actually hit. The reproduce-vs-derive ceiling is § 12 with the M8.5-A coexact module as the worked instance. The T5 gate this close releases: the M8 column no longer has a frozen document pinning a live task path.

**T5 CLOSED: THE MIGRATION IS DECLINED, AND ISSUES BECOME PLATFORM ISSUES (2026-08-01, user decision).** The evaluation was filed with a decline as a first-class outcome and that is how it closed. Three reasons, the first the evaluation had underweighted: a roadmap edit is a tracked diff, attributable and revertable, which is what a file several authors touch needs, while an issue body edits in place with a deletable history; author permissions were never the whole cost, since the fixed no-triage intake model leaves the column maintainer-operated either way; and the maintainer's transcription-plus-validation load survives the migration, so the friction the task was filed on is relocated rather than deleted. The price is accepted and named: a fork-based author's tracking edit stays a full pull-request cycle. The boundary rule is replaced by its reverse in [§ CONVENTIONS](#conventions), and [`ROADMAP_STANDARDS.md`](ROADMAP_STANDARDS.md) plus its checker are no longer retiring. Before the open issues close, all twelve were audited into roadmap homes, three of them new rows: [T5](tasks/t5_task_details.md).

**T7 CLOSED: THE ROUND TRIP WAS THE OVERHEAD, NOT THE RIGOR (2026-08-01, user question).** [T5](tasks/t5_task_details.md) was filed on this exact pain, "the coordination edits alone took three reviewed merges", and answered that issues are not the cure; T7 measured what is. M8 and M5 carry the same doc-to-code ratio (1:3.2 against 1:3.1), so documentation volume is not the difference between the columns. Round trips are: 12 of 26 M8 pull requests were sub-200-line document syncs, against roughly 4 of 25 on M5, because M8 has two parties and M5 has one. #374 → #375 → #376 → #378 spent four merges on one amendment, the last recovering fixes orphaned by the first two. The habit is making the agreement in the merge history instead of the PR thread, and it is cheap to change because it moves when an edit lands, never whether it is checked. The rule: [`CONTRIBUTING.md § How review works`](../CONTRIBUTING.md#how-review-works). Nothing in the verification layer moved. Every blind protocol, mutation test, gate and freeze stands, since their measured catch rate is what justifies them.
